# C06ae — Synchronous terminal diagnostics batches

Date: 2026-11-09 (Asia/Bangkok). Baseline: `11502389`; user reported C03au built successfully and requested a larger implementation batch. Scope: P1-77 in the shared rootfull/roothide/TrollStore application license lifecycle coordinator. TouchPOC is excluded.

## Three lifecycle operations

Group the terminal diagnostics of refresh, activation and deactivation. Refresh has separate success/failure groups; activation and deactivation each group their common callback body. Success combines result/history, license-change metadata and operation completion; failure combines result/backoff/history and completion. Four synchronous call sites cover all six outcomes.

The initial begin/attempt update remains immediate, so pending work is still visible while HTTP is running. Manager calls, refresh decision/backoff reads and the successful refresh's localStatus verification remain outside the new batch monitor. Signed persistence, verifier/generation/authority policy, manager request counts, completion/notification order, UI snapshot worker and coalesced daemon reload worker retain their preceding source. The batch includes only synchronous metadata mutations and accepted publication/completion enqueue steps, not network or queued-worker residence.

Each outer batch holds the existing coordinator monitor until its final flush. Nested calls join that owner. The first actual mutation performs the original directory preparation and fresh plist read; an empty group does no IO. Later mutations begin from an independent shallow working dictionary. After the existing mutation/history/values/mode/time steps succeed, validate the property-list graph, encode it as XML and decode it into an immutable owned snapshot in memory. Only that completed snapshot replaces the pending state. A local serialization pool retires encoded temporaries before the update returns. Thus a throwing mutation cannot publish a partial prefix, and later caller changes to mutable strings, data or nested containers cannot alter an earlier accepted update. Invalid property-list updates keep the last accepted state rather than poisoning the final file.

The public diagnostics getter copies the pending immutable snapshot when called reentrantly inside a batch. Its usual live request/UI/performance overlays remain. Other threads acquire the monitor before the fresh file read, so they cannot load an old file and then wait behind a batch. Nothing is cached across groups: the next independent update/read returns to persistence and sees external replacements. Staged snapshots follow the preceding XML write/read normalization, including unsigned integer boundaries and fractional dates. A CF deep copy is insufficient here: an Apple Windows CoreFoundation probe reproduced UINT64_MAX narrowing to -1, matching the failing snapshot field's boundary.

## Commit and failure semantics

The outer finally detaches the pending snapshot and clears ownership before invoking one atomic plist writer. Empty groups do not write. Standalone updates retain their original immediate writer. Nested groups do not flush early. No timer, asynchronous flush queue, cross-process cache, retry or background task is introduced.

Completion and notification blocks are enqueued within the terminal group. Main can run an enqueued completion before the decision owner returns from its final flush. An unlocked direct file reader can still observe the preceding attempt at that point; the public diagnostics getter acquires the coordinator monitor and waits for the group. Callback delivery does not acknowledge auxiliary diagnostics persistence or durability.

Diagnostics are auxiliary to the already completed manager result. A NO return or NS/C++ exception from the final batch writer is best effort: discard the snapshot, release admission and do not replay the manager operation, UI publication or reload. A flush exception cannot mask a primary mutation exception. Read/mutation exceptions still propagate through the preceding operation handlers after finally cleanup. The next independent update reads the file again; it does not silently retry a failed group.

External file readers see the preceding persisted diagnostics until the single final write. A crash/write failure can lose the whole terminal diagnostics group, whereas the old sequence could leave intermediate updates. This changes auxiliary visibility and failure granularity, not signed lease commit or runtime licensing authority. The existing per-process monitor is not a cross-process transaction protocol; external concurrent writers retain last-writer limitations, now over the wider read-to-group-flush window. XML serialization/decoding remains per accepted mutation; the final flush additionally serializes the last snapshot. This favors persistence compatibility and fewer file operations, with no CPU improvement promised. Broader synchronous monitor residence, codec/validation costs, opaque filesystem work, plist size and device latency/RSS remain unmeasured. No hard IO/time/process-memory bound is claimed.
