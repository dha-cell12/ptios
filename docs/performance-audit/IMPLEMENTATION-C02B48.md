## Result and compatibility

The rootfull/roothide JS timer branches call TLinkExecuteNativeSetTimer/TLinkExecuteNativeRemoveTimer directly. RAW and direct paths share TLinkSetTimer/TLinkRemoveTimer, extracted around the existing scanner, interval policy and synchronous scheduler owner operations. Both RAW task handlers remain unchanged. Production TrollStore and TouchPOC execution sources are unchanged; both workflows run shared safety suites. No CPU, allocation, latency or RSS improvement has been measured.

Ordinary typed calls avoid full RAW task formatting/encoding/splitting, processTaskWithContext, compatibility CF stream and response-vector accumulation/copy. Keep input snapshots, per-interval three-decimal formatting, NSScanner validation and bounded error/ACK formatting. Set still formats the interval with %.3f before scanning and converting to nanoseconds, rather than passing the original double straight to the timer. Thus small positive JS values can round to zero and be rejected; values near the one-second repeat boundary keep Foundation's old rounding. Finite/positive JS checks, doubleValue/boolValue/default conversion order and protocol-string validation remain unchanged.

Set admission counts name, script, rendered interval, task, three separators and repeat digit against 8192 UTF-16 units before UTF-8 byte/NUL/encoding checks. Remove counts its entire name plus two task digits. Single semicolons can overlap inserted separators even when JS token validation passes. A bounded set-field join/split preserves these overlaps, first-four-field selection and parsed repeat intValue; ordinary text bypasses splitting. Remove takes the complete name as before. Extra/missing arguments and exact errors retain their existing behavior.

The shared set core retains NSScanner scanDouble/isAtEnd, finite/positive/range policy, repeat >= 1 second, one-shot positive subsecond support, name/script validation order and truncating seconds-to-nanoseconds conversion. Registry mutation, GCD source creation/configuration/resume and callback installation still run on the same serial owner. Failed source creation and generation exhaustion keep their errors and suspended-source cancel/resume cleanup. Remove stays synchronous and acknowledges after its owner mutation, including waiting behind an already-admitted callback. Callback busy admission, generations, one-shot consumption, launch-time license recheck and script preparation remain unchanged.

## Authority, effects and lifetime

Set and remove each retain one ordinary task-38/task-39 license gate. Remove is not a cleanup exemption, and owner automation authorization does not bypass either gate. Child contexts preserve owner fields, inherited deadline/cancellation/output settings and disable response capture. Neither task adds C01. Stop is checked after conversion, before/after the gate and after backend work, before the bounded reply. Scoped budgets and per-call pools restore TLS and retain snapshots/errors/results; the registry retains each installed script as before.

Scheduler owner dispatch is opaque synchronous work. A set/remove can commit after caller cancellation/deadline and then report stop or output rejection. No queued-operation cancellation, timeout extension, early output floor, retry, rollback or new propagation of caller TLS onto the owner is added. Future callbacks retain their existing admission/license policy rather than the scheduling call's budget. Escaping caller-boundary NS/C++ faults normalize to native_exception; this does not promise safe exception propagation across libdispatch. Real callback delivery, timing, thread and device behavior need qualification.
